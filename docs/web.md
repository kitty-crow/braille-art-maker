# Web app

The hero starts in **Colour** at 256 cells with Atkinson dithering, 0.55 contrast, 1.20 detail and +0.25 threshold bias. **Full Colour** starts disabled. Turning Colour off restores the original monochrome profile: 96 cells, Ordered 4x4, 1.12 contrast, 0.34 detail and +0.015 bias.

The studio starts monochrome with 96 cells, 1.12 contrast, 0.34 detail, +0.015 threshold bias and Ordered 4x4. The Resolution slider supports 24 through 2048 horizontal Unicode cells. Resolutions above 256 cells are experimental because browser rendering, memory use and embed generation become much heavier.

Pointer dragging encounters three deliberate resistance gates. At 256 the slider pauses with the experimental-range warning. At 765 it pauses again with **“Beyond here, any-nyan ventures at their own risk. Extreme resolutions can devour memory, battery, and occasionally the tab itself.”** At 1024 it pauses with **“1K? Are nya crazy?! I’d hate to be your RAM right meow!”**. Pushing deliberately through each gate continues the same drag. Keyboard changes are not trapped by pointer resistance.

The slider ends at 2048 because that is the highest range confirmed to work reliably in real-device testing. The numerical Resolution field intentionally has no 2048 maximum. A value such as 8192 or 10240 may be typed manually; committing a value above 2048 shows a native Yes/No confirmation warning that the request is unsupported and may crash the tab. Cancel restores the previous value. Confirm passes the exact requested integer to the engine without a hidden upper clamp. This is deliberately an unsupported escape hatch rather than an endorsed operating range. The core and CLI likewise do not impose an arbitrary upper resolution clamp.

Resolution changes use a settle-before-render model. Dragging the slider or typing a number updates the controls immediately but does not repeatedly regenerate art for every intermediate value. The target resolution is committed when the range interaction finishes or when numeric entry is committed by change, blur or Enter.

Above 256 cells the final target-resolution preview is painted progressively and asynchronously. The art itself is computed once at the selected resolution; the renderer creates the final row slots and fills even rows first, followed by odd rows. Rendering runs continuously at full speed and yields cooperatively only after approximately 12 ms of actual rendering work, using `scheduler.yield()` where available with a lightweight task handoff fallback. There is no deliberate animation-frame sleep between batches, so sufficiently fast renders may finish before progressive drawing is perceptible.

The preview always remains genuine Unicode. Through 256 cells the studio uses the exact per-cell grid. At higher resolutions it first tries the compact row renderer only when all 256 Braille glyphs pass an exact geometry proof at the actual rendered size. When that proof fails at very high resolutions, the exact fallback uses fixed-position Unicode chunks instead of one DOM element per cell. Chunk width scales with the square of resolution, keeping the live chunk-node count roughly bounded even for manually-entered values well above 2048 while repeatedly resetting glyph drift. Colour backgrounds are continuous per row to avoid compositor seams. No preview or embed is rasterised.

The browser studio deliberately exposes only two colour controls. **Colour** means foreground-only colour on the normal Unicode mask. **Full Colour** enables the adaptive two-colour foreground/background representation. There is no separate background-only checkbox. Enabling Colour leaves the slider values alone, switches the dither control to Atkinson and starts with Full Colour off; disabling Colour switches dithering back to Ordered 4x4. The lower-level `colourBackground` setting remains accepted for backwards compatibility, but is not exposed as a browser mode.

The canvas control is the first checkbox. In light mode it is **Dark canvas** and forces the preview onto a dark surface when enabled. In dark mode it becomes **Light canvas** and forces the preview onto a light surface when enabled. Its initial automatic choice follows the visibility rules: dark theme uses a dark canvas, and light foreground-only Colour also uses a dark canvas. Once the user changes the canvas manually, later theme/colour changes keep the actual selected surface. Changing the canvas also aligns Invert with the selected surface; Invert remains independently adjustable afterwards.

**Reset sliders** restores only Resolution, Contrast, Detail and Threshold bias to 96, 1.12, 0.34 and +0.015. It does not change Colour/Full Colour, dithering, canvas or polarity.

When foreground-only Colour is shown on an actual light canvas, the question-mark tooltip warns that some colours can be difficult to see. This applies whether the page theme itself is light or the user has explicitly enabled Light canvas in dark mode.

Paste-ready embeds use the same safety rule: with `data-surface="auto"`, foreground-only Colour on a resolved light theme receives the dark surface. Full Colour output follows the normal theme surface. The consuming site may explicitly set `data-surface="light"` if it accepts the readability trade-off.

The latest completed studio result is persisted in IndexedDB for fast refresh restoration. The cache uses database `unicode-art-studio-cache` schema v2 with separate session, compact-art and embed stores. Art is stored as a Blob containing the same lossless bounded binary representation used by high-resolution worker handoff; the finished embed is stored as a Blob as well. Source/configuration metadata are retained so the editable vector stage can be reconstructed quietly after the cached Unicode preview is already visible. Cache entries are scoped to the current app version, so incompatible output from an older release is not silently reused.

IndexedDB is only a persistence cache. It is **not** used as the live high-resolution worker transport and the page never stores or retrieves the giant live `Art`/`cellColours` object graph there. The old legacy object store is left untouched during schema upgrade for non-destructive migration, while all current writes use the compact v2 stores. If IndexedDB is unavailable or a cache write fails, the studio continues normally without persistence.

The embed fragment uses lossless `u4` transport. Through 256 cells it can run the full optimiser. Above 256, the browser uses a bounded-memory exact path: the page serialises one chunked lossless raw payload, snapshots that same payload for the persistence cache, then transfers its `ArrayBuffer` to the Worker rather than structured-cloning the potentially huge `Art`/colour object graph. The Worker compares raw, maximum-DEFLATE and Brotli-11 transport for that exact payload and is disposed after the high-resolution one-shot job so Brotli/WASM high-water memory can be released. High-resolution preview rendering completes before embed compression begins, reducing simultaneous peak memory.

Compact defaults to the shortest super-compact basE91/J8192 representation. The optional **Payload as a story** checkbox regenerates only the embed and represents the same compressed bytes as reversible Japanese prose. Its tooltip explains the trade-off and points to the README's **Compact payload modes** section. Story mode is larger but remains one physical payload line. Large story payloads are divided into bounded 256-byte Japanese chapters so no single unbounded `BigInt` is created.

While embed encoding runs, the studio shows **Generating embed** and an **Encoding art…** progress bar; once encoding reaches 100%, that progress UI is hidden. Encoding itself is not delayed for the sake of displaying progress. New copied embeds contain only readable host attributes, one self-identifying payload script and one loader script; the CDN runtime reconstructs the Shadow DOM scaffold and shared stylesheet. The fragment itself is displayed through Marked, DOMPurify and Highlight.js.

Browser TXT, HTML and SVG downloads are content-addressed as `kitty-crow-github-io-unicode-art-studio-{sha256}.{ext}`, using the SHA-256 of the exact downloadable bytes.

The browser app and embed Worker URLs are release-versioned in the generated site so mobile browsers do not keep executing a stale high-resolution implementation after deployment.

All source HTML pages use the shared mobile viewport contract: `width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no`.

The top navigation is a sticky floating bar and remains pinned near the top of the viewport while the page scrolls.

Each range control and Compact payload option has an accessible info button. Pointer hover follows the cursor with a tooltip; keyboard focus shows the same explanation beside the button.
